# v0.12.0 — MCP Modernization: Design

Date: 2026-07-31
Status: Approved for implementation (autonomous session; scope taken from ROADMAP.md v0.12.0)

## Problem

The server speaks MCP but uses none of the capabilities the 2025-11-25 spec
revision added, and it is invisible to the official MCP Registry. Concretely:

- The two update tools block the connection for up to 300 seconds with no
  progress and no way to do anything else meanwhile.
- Every tool returns an opaque TOON string. Clients that can consume
  `structuredContent` get nothing machine-readable, and no tool declares an
  output schema.
- `get_laravel_learning_path` called with no arguments dumps a listing instead
  of asking the one question ("which path?") the protocol now lets it ask.
- The HTTP transport has no authentication story beyond "put a proxy in front".
- The server is not in the MCP Registry, has no `server.json`, no server
  version reported at initialize, no icon, and no `.well-known` discovery
  endpoint.

## Scope

In: the four ROADMAP v0.12.0 spec items (tasks, elicitation, structured
outputs, OAuth 2.1), registry publishing (`server.json`, publish workflow,
`.well-known`, OCI label), server icons (SEP-973, trivial), and a server
version constant (prerequisite for registry work).

Out: the ROADMAP "Documentation Improvements" bullets (advanced search,
version filtering, ecosystem mapping) — vague, unrelated to the spec work, and
this branch is already large. They stay on the roadmap. Also out: the
2026-07-28 release candidate; we target the current stable revision
(2025-11-25), which is `LATEST_PROTOCOL_VERSION` in our installed SDK.

## Verified feasibility (FastMCP 3.4.5, pinned `<4`)

Everything below was probed against the installed package, not docs:

- `fastmcp[tasks]==3.4.5` installs (`fastmcp-tasks`, docket, redis client).
  With it, `@mcp.tool(task=True)` on an async tool negotiates the `tasks`
  capability over protocol 2025-11-25, and the in-memory client completes a
  full submit → `working` → `completed` → result round-trip. Sync clients fall
  back to synchronous execution ("optional" mode). Sync tools raise at
  registration — task tools must be `async def`.
- `ctx.elicit()` supports scalars, enums (titled, multi-select), dataclasses,
  and defaults; raises when the client lacks the capability.
- `ToolResult(content=..., structured_content=...)` lets a tool return TOON
  text and structured JSON side by side; `output_schema=` is a tool decorator
  kwarg.
- Auth: `JWTVerifier(jwks_uri|public_key, issuer, audience, required_scopes)`
  and `StaticTokenVerifier` exist under `fastmcp.server.auth.providers.jwt`;
  `FastMCP(auth=...)` wires them.
- `FastMCP(version=..., icons=[Icon(src=...)])` accepted at construction.

## Design

### 1. Server identity (prerequisite)

`SERVER_VERSION` constant in `laravel_mcp_companion.py`, passed to
`FastMCP(version=...)` along with `website_url` and an `Icon` built from
`icon.svg` as a base64 data URI (self-contained; no network fetch). The
existing version-consistency guards in `tests/unit/test_version_consistency.py`
gain assertions that `SERVER_VERSION` and `server.json`'s `version` match
`pyproject.toml`. `package.json` is stale vestigial metadata at 0.8.0,
referenced by nothing — delete it.

No version bump on this branch. Changes land under `[Unreleased]`; the release
commit bumps pyproject/ROADMAP/README/SERVER_VERSION/server.json together.

### 2. Tasks (SEP-1686, experimental)

`update_laravel_docs` and `update_external_laravel_docs` become
`async def` with `task=True` (execution mode "optional": task-capable clients
get a task handle and poll; everyone else keeps today's synchronous behavior,
so this is non-breaking). Their blocking bodies move behind
`anyio.to_thread.run_sync`, which also stops them starving the event loop in
sync mode — a live bug today: a 300-second update freezes the whole server for
every connected HTTP client.

In-memory task backend only (`memory://` default). No Redis, no extra worker
processes — single-process server, YAGNI.

Progress reporting inside the updaters (per-service callbacks) is deferred;
the task status transitions themselves are the deliverable.

### 3. Elicitation

One flagship use, per the roadmap wording ("interactive learning path
customization"): `get_laravel_learning_path` with no `path_name` asks the
client to pick a path via a titled enum built from `LEARNING_PATHS` (10
entries, each with name/description/difficulty). Decline/cancel and clients
without the elicitation capability fall back to exactly today's behavior (the
listing) — wrapped in `try/except` since FastMCP raises on unsupported
clients. The tool becomes `async def`; the impl split stays (elicitation lives
in the closure, `get_laravel_learning_path_impl` stays pure and sync).

No other tool gains elicitation in v0.12.0.

### 4. Structured tool outputs

TOON stays. Structured content is added alongside it, not instead of it:
a helper in `toon_helpers.py`, `toon_result(data: dict) -> ToolResult`,
returns `ToolResult(content=[TextContent(toon_encode(data))],
structured_content=data)`. The spec asks that text content be a functional
serialization of the structured content — TOON satisfies that.

Converted in v0.12.0 (the tools whose output is genuinely tabular/structured
and already flows through TOON formatters): `search_laravel_docs`,
`laravel_docs_info`, `get_laravel_package_recommendations`,
`get_laravel_package_info`, `list_laravel_docs`. Each declares `output_schema`.
Prose-shaped tools (doc reads, learning paths) stay plain strings — forcing a
schema onto markdown bodies is noise.

Open risk, resolved by test: whether the `search` transform's `call_tool`
proxy forwards `structuredContent`. If it does not, structured output still
reaches `--transform-mode none` users and the pinned `search_laravel_docs`;
the test documents whichever behavior holds.

### 5. OAuth 2.1 (resource server, HTTP transport only)

The server becomes an OAuth 2.1 *resource server* — it validates bearer
tokens; it does not issue them. New flags, each mirroring an env var, all
HTTP-only (ignored with a warning on stdio):

- `--auth-jwks-uri` / `AUTH_JWKS_URI` — JWKS endpoint of the authorization
  server
- `--auth-issuer` / `AUTH_ISSUER`, `--auth-audience` / `AUTH_AUDIENCE`
- `--auth-required-scope` / `AUTH_REQUIRED_SCOPES` (repeatable / CSV)
- `AUTH_STATIC_TOKENS` (env only, deliberately no flag: token→client mapping
  for dev/internal use, format `token:client_id[,token:client_id...]`), which
  wires `StaticTokenVerifier`. Mutually exclusive with JWKS config.

When configured, requests without a valid token get 401 with
`WWW-Authenticate`; FastMCP serves `/.well-known/oauth-protected-resource`.
When not configured, behavior is unchanged, and the README keeps saying so.
JWKS config requires `--auth-issuer` and `--auth-audience` — refusing
audience-less JWT validation is the difference between auth and theater.

### 6. Registry publishing

- `server.json` at repo root: `$schema` (2025-12-11 registry schema), name
  `io.github.brianirish/laravel-mcp-companion`, description, `version`
  matching pyproject, one `oci` package pointing at
  `ghcr.io/brianirish/laravel-mcp-companion:<version>` with `stdio` transport
  and the runtime arguments users need (`docker run --rm -i`).
- Dockerfile gains `LABEL io.modelcontextprotocol.server.name=
  "io.github.brianirish/laravel-mcp-companion"` — the registry validates
  OCI ownership through this label.
- Publish workflow: **GitHub Actions**, not Harness, because registry
  authentication uses GitHub Actions OIDC (`mcp-publisher login github-oidc`)
  and that credential only exists there. New
  `.github/workflows/publish-mcp.yml`, triggered on `v*` tags only (docs-*
  syncs must not publish): wait for the `ghcr.io` image for that tag to exist
  (poll with timeout — Harness builds it concurrently on the same tag), stamp
  the tag version into `server.json`, `mcp-publisher publish`. The dormant
  ci/release workflows stay dormant; this is a new, active, single-purpose
  workflow.

### 7. `.well-known` discovery (HTTP mode)

`GET /.well-known/mcp/server.json` on the HTTP app serves the repo
`server.json` (with the live `SERVER_VERSION` stamped in), the path the
registry documents for self-hosted discovery. Added via FastMCP custom route
if available in 3.4.5, else a Starlette route on the app built in `main()`.
stdio mode: nothing to serve, nothing changes.

## Testing

- Protocol tests (`tests/protocol/`, in-memory `Client`): tasks capability
  advertised and full task round-trip for `update_laravel_docs` (updater
  mocked); sync fallback still works; elicitation flow for
  `get_laravel_learning_path` using a client elicitation handler (accept,
  decline, and capability-absent paths); `structuredContent` and
  `outputSchema` present for converted tools; server version/icon in
  initialize result.
- Unit tests: auth flag validation (mutual exclusion, issuer/audience
  required, stdio warning); `toon_result` helper; version guards extended to
  `SERVER_VERSION` and `server.json`.
- HTTP tests (existing patterns in transport security tests): 401 +
  `WWW-Authenticate` when auth configured, `.well-known/mcp/server.json`
  served, `/.well-known/oauth-protected-resource` present when auth on.
- `server.json` validated against the published schema in a unit test
  (offline: vendor the schema or assert required fields — no network in tests).

## Risks

- `fastmcp[tasks]` adds docket/redis-client deps to the image (~ a few MB).
  Accepted; in-memory backend means redis is never contacted.
- Tasks are experimental in the 2025-11-25 spec; "optional" execution mode
  means nothing breaks for clients that ignore them.
- Registry is in preview; publish failures are non-fatal to the release (the
  workflow is independent of the Docker push).
- The 2026-07-28 RC will change tasks (SEP-2663); revisit when FastMCP 4 /
  the final spec lands. Pin stays `<4`.
